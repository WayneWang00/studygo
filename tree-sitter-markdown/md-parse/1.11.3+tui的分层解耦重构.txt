# 1.11.3 tui的分层解耦重构
## 为什么要重构

老的tui.c分层不够清晰。在命令的执行函数中，会直接向终端输出错误信息。

按照机制策略分离原则，这是设计不灵活的表现。

这样做带来的后果是：

1.  不方便单元测试，逻辑层和IO层耦合，必须保证有合法的终端才可以正确测试；

2.  在批处理，或者非交互模式中执行命令，会输出错误串，这相当于固化了错误处理策略。导致tui_batch_file无法静默执行。

所以，需要对tui.c做一个小小的重构，将IO层和逻辑层彻底分离。


```

# 1.11.3 tui的分层解耦重构
## 怎么重构的
### 步骤二、构筑不同层之间的中间层

如果解析执行命令过程中发现错误，需要通知到用户怎么办？这个要求，会导致IO和逻辑层之间产生耦合。

解除耦合的方法，就是构建中间层，即tui_t中的last_error_no,last_error_str，逻辑层发现错误不直接输出到终端，而是先输出到last_error_no,last_error_str。

如果，tui_t当前处于交互模式，则调用命令解析处理的函数，即tui_on_event，可以从这两个变量中获取错误信息，输出到终端。

如果，tui_t当前处于非交互模式，比如tui_batch_file，则从这两个变量中获取到错误信息后，输出到日志。


```

## 怎么重构的
### 步骤三、把逻辑分离到合适的层次

因为原始的代码分层解耦不清晰，重构就是要利用新构建的中间层，重新梳理逻辑，把IO层的代码从逻辑层彻底清除。

方法：查找tui_on_event调用树涉及到的函数范围，找出所有调用tui_printf输出错误信息的代码，替换成输出到中间层的tui_set_error函数。

经过这样一个小小的替换，逻辑层和IO层的代码就彻底分开了。

具体过程发生的变化，可以对比重构前的源码tui-old.c和重构后的源码tui-refactor.c。

# 1.11.3 tui的分层解耦重构
## 怎么重构的
### 步骤四、彻底分离不同层次的代码

经过上述分离，IO层和逻辑层已经完全分开，不再耦合。但是，如果后续维护者没有注意到这一点，继续添加逻辑，很可能又会让逻辑层和IO层耦合到一起。

怎么办，可以把不同层的代码物理上彻底分开，即把不同层的代码分离到不同的编译单元中。

这里没做这么彻底，仅仅调整了一下函数位置，把逻辑层和IO层代码分别挪到一起，通过注释的方式说明两层代码的区别。

具体，可以参考调整后的tui-new.c文件。有兴趣的可以尝试把两层逻辑彻底分离到两个独立编译单元。
