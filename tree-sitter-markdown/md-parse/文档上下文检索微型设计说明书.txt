# 1.**介绍**
## 1.1.**目的**

*简要介绍设计或修改该模块的目的，说明书要描述和解决的主要问题，和使用该规格书的对象(及各对象需要关注的内容等)。*

当前costrict通过在System Prompt
中预置grep+read_file工具，实现大模型自动调用检索工具对项目内代码、文档进行检索以整合上下文的能力。但grep+read_file基于关键词匹配，在语义理解、跨文档关联等场景存在明显局限性。为提升文档检索精准度，改善大模型回答质量，拟对文档引入向量检索技术，用于检索项目内相关的markdown、OpenAPI文档上下文。

 

●markdown文档

  -------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------
  文档类型       用途

  readme         项目入口说明，包含项目简介、安装步骤、快速启动、目录结构、贡献指南、常见问题等核心信息，帮助用户快速了解和使用项目。

  技术文档       涵盖技术架构（如微服务架构、前后端分离架构）、技术选型（框架、数据库、中间件等）、核心模块实现原理、关键技术难点解决方案、代码规范等，为开发人员提供技术指导。

  设计文档       包含需求转化的设计方案，如 UI/UX 设计规范、数据库表结构设计、接口设计（非 API 文档的详细设计思路）、业务流程设计、模块交互设计等，指导开发和测试工作。

  API 文档       详细描述项目接口信息，包括接口名称、请求方法、请求

● OpenApi文档

OpenAPI 协议（OpenAPI Specification，简称 OAS）是一套用于标准化描述
RESTful API 的开放规范，其核心目标是让 API
的设计、文档、测试、调用和代码生成实现自动化与标准化，解决不同团队、不同工具间对
API 理解不一致的问题。它前身为知名 API 工具 Swagger 的核心规范，2015
年移交 Linux 基金会管理并更名，目前已成为 API 领域的事实标准。

目前主流版本为 OpenAPI 3.0.x（兼容性最广）和
3.1.0（功能最全面），大部分工具已支持这两个版本。 库依赖文档。

  -------------- --------------------- ----------------------------------------------------------------
   **使用场景**        **格式**                                  **原因分析**

    机器解析 /     JSON/YAML（原生）    规范定义的标准格式，所有工具（代码生成、测试）均支持。（标准）
      自动化                           

    手动编写 /       YAML（原生）           支持注释、缩进清晰，可读性远优于 JSON，适合人类编辑。
       维护                            

   团队静态分享        Markdown               兼容 GitHub 等平台，易嵌入项目文档，无需依赖工具。

    交互式调试       HTML（Swagger                   支持在线测试接口，前后端协作效率高。
                      UI/Redoc）       

    离线归档 /         PDF/Word            适合离线保存或满足企业级文档交付规范（如客户合同附件）。
     正式交付                          
  -------------- --------------------- ----------------------------------------------------------------

OpenAPI 文档的核心是 JSON 和 YAML 两种原生格式（遵循 OpenAPI
规范，机器可解析），而 Markdown、HTML、PDF 等是基于原生格式转换的
衍生可读格式（人类友好，用于展示和协作）。实际开发中，通常的流程是：

●开发人员用 YAML 编写 OpenAPI 原生文档（便于维护）；

●通过工具转换为 HTML（Swagger UI） 用于前后端交互式调试；

●转换为 Markdown 嵌入项目 README 用于团队同步；

●按需导出 PDF 用于离线归档或交付。

# 1.**介绍**
## 1.1.**目的**
### **1.1.3 当前痛点（基于grep+read_file）**

 

（1）语义理解缺失，精准度低

仅依赖关键词匹配，无法理解用户意图。例如用户查询 "如何避免 Java
空指针"，grep可能只返回包含 "空指针" 的文档，漏掉 "Optional
类""Objects.requireNonNull" 等关键内容。

 

（2）难以处理同义词 / 变体词

对 "接口" 与 "API"、"参数" 与 "入参" 等近义词无识别能力，导致查询不全。

 

（3）跨文档关联能力弱

只能按关键词检索单个文档片段，无法整合多文档的关联信息。例如查询
"用户登录流程" 时，无法同时关联 "认证文档""权限文档""Token 存储文档"
的内容。

 

（4）长文档处理效率差

对超过 100
页的文档，grep可能返回大量包含关键词的冗余内容，大模型需从中筛选有效信息，导致回答冗长或遗漏关键细节。

 

（5）模糊查询支持不足

当用户描述不精确时（如
"怎么让前端页面加载更快"），grep因无语义联想能力，常返回无关结果，迫使用户多次调整关键词。

# 3.**模块详细设计**
## **3.2 markdown解析切块**

 

●结构优先：以 Markdown 原生的标题层级（# 至
######）为核心切分锚点，所有切块均基于标题结构展开，确保切分逻辑与文档的自然阅读逻辑一致。
（一级-二级标题-三级标题，上级+当前级；怎么切，效果更好；真实测试案例，公司设计文档、需求文档）

●语义独立：每个切块必须包含 "完整且独立的语义单元"------
即能单独表达一个明确的信息点（如一个步骤、一个定义、一组参数、一个问题解答），避免拆分后信息碎片化。

●特殊元素不拆分：对 MD 中的代码块（\`\`\`）、表格（\|）、有序 /
无序列表（1./-）、公式（\$） 等特殊元素，视为
"不可拆分的语义整体"，需与前后关联的说明文本绑定为一个切块，禁止割裂。

●粒度均衡：统一控制切块粒度在 "中等粒度" 为主（单切块字符数建议 150-800
字，可根据内容密度微调），避免过粗导致信息冗余、过细导致语义断裂。

●块间重叠：块与块之间增加20%重叠，增强文档块关联性。

 

markdown 解析使用开源库，如 [GitHub - yuin/goldmark: :trophy: A markdown
parser written in Go. Easy to extend, standard(CommonMark) compliant,
well structured.](https://github.com/yuin/goldmark) 。
