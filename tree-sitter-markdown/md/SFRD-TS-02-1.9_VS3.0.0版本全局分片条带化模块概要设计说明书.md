# 介绍

## 目的

简要介绍该说明书的目的，和使用该规格书的对象(如项目技术经理等)。

本说明书描述全局分片与条带化功能的基本原理、各种流程处理，供编码人员和项目技术经理参考。

## 定义和缩写

定义或解释本文档中使用的所有专用名词和缩略语。

shard：全局分片

stripe：条带，或指分片中的条带功能

stripe size：条带大小，也叫条带深度，指条带数据块的大小

stripe width：条带宽度，指同时可以并发读或写的条带数量

stripe chunk：条带数据块，每个数据块的大小为stripe size

xlator：translator的缩写，表示glusterfs内部一个独立的模块，可以动态开启和关闭，各个xlator之前形成一个调用栈的关系。

# 概要说明

## 背景描述

### 工作原理

旧版本也有分片功能，位于brick端的BD层。一个文件经由AFR分成两个副本，每个副本在服务端以16G大小的块进行切分，在单个磁盘容量不足的情况下，可借用本主机内其他磁盘的空间，从而突破单磁盘容量的限制，使文件大小最大能达到单个主机的容量。

![图 4‑1 BD分片方案](media/image4.png){width="6.261111111111111in"
height="4.430555555555555in"}

这个方案的弊端：

1.  会造成磁盘空间使用不均衡

2.  单个文件无法使用整个卷的空间

3.  单个文件只能使用单个SSD的性能

全局分片依然采用类似的原理，即对文件按照固定大小进行切分。不同的是，全局分片采用客户端分片方式，各个分片的分布位置由分布框架和分布算法决定，可分布在卷中的所有主机上。由于分片的存放位置不再局限于单个主机内，因此可以使文件使用整个卷的空间。

并且，在分片的同时引入条带化功能，使单个文件可以使用多个SSD的性能（分布算法会优先将一个条带组内的分片分不到不同的磁盘组上）

![图 4‑2
全局分片和条带化效果](media/image5.png){width="6.259027777777778in"
height="3.2180555555555554in"}

如上图所示，假设文件的分片大小为16GB，条带宽度为4，条带深度为128K。那么该文件的前64GB数据会存放在前4个分片中（不管有没有条带都是这样，这个是由分片决定的）。而增加条带化效果后，会把连续的数据分割成128K大小的数据块，每段数据分别写入各个分片。

### xlator实现

- 方案一

       方案                                    方案一                                                      方案二                                         备注

       性能       两个模块各自独立成xlator，在调用时多一层栈帧，有增加IO时延的风险   在同一个xlator内部处理分片与条带化逻辑，无时延增加           尽量降低对性能的影响

由于方案一可能对性能产生影响，且增加工作量，综合考虑，选择方案二。

### 文件大小处理

- 方案一

文件大小记录在首分片的扩展属性，获取文件大小时直接从首分片扩展属性中获取即可，而更新时则要发往首分片更新。对于每一个IO，只要是追加写到文件末尾，导致文件大小变大的，写IO返回到全局分片这一层，还需要额外发送请求到首分片修改文件大小，再返回当前IO给上层。

- 方案二

首分片只记录当前文件最后一个条带组的编号。获取文件大小首先需要从首分片中获取最后一个条带组的编号，然后再获取最后一个条带组所有分片的大小，经过计算后得出文件的大小。更新大小也需要发往首分片更新，但是只有当文件大小增长量超过一个条带组的大小时，才需要更新该编号。

下面是两个方案的对比：

  -------------------- ------------------------------------------------------------------------------------------------------------------------------ ------------------------------------------------------------------------------------------------------------------------------- --------------------------------------------------------------------------------------------------------------------------------------
                                                                                   方案一                                                                                                                         方案二                                                                                                                               备注

         写性能         为了确保文件大小正确，如果本次IO改变了文件大小，无论增加量有多小，都则需要往首分片修改扩展属性再返回IO，追加写严重影响性能。   文件大小每增加一个条带组大小时，才需要更新编号。以分片大小=16G，条带宽度=4为例，当文件大小增长超过64G时，才需要更新一次编号。   当前HCI环境下qcow2文件会在需要分配空间时预分配128M，因此不会出现频繁刷新文件大小的问题。但是为了做得更通用，不能以此背景去选择方案。

   对lookup的性能影响                                                       低，只需lookup首分片                                                             中，除了lookup首分片，还需要额外对最后一个条带组的分片进行lookup以获取其分片大小。（对条带组分片的lookup可并发）         
  -------------------- ------------------------------------------------------------------------------------------------------------------------------ ------------------------------------------------------------------------------------------------------------------------------- --------------------------------------------------------------------------------------------------------------------------------------

由于方案一有较大的IO性能风险，因此最终选择方案二。

### 文件blocks属性处理

- 方案一

blocks直接通过size计算得出：blocks = size / 512。

- 方案二

内存中维护所有分片真实占用的空间，经过汇总会再设置到首分片的扩展属性，即操作的是绝对值。获取blocks属性时直接从该扩展属性中获取。

- 方案三

内存中对只维护当前已打开的分片的blocks属性，当某个分片的blocks属性发生改变，计算出差值然后加到首分片的扩展属性中，即操作的是相对值。获取blocks属性时直接从该扩展属性中获取。

以下是各方案的对比：

  -------------------- -------- ------------------------------------------------ --------------------------------------------------------------------------------------------------------------------------
                        方案一                       方案二                                                                                方案三

  blocks准确性            低       高，即使某次请求设置失败，进行重新设置即可     中，当无异常时，准确性没问题。当某些请求更新失败，并且客户端进程重启，那么会丢失部分值。这种误差会一直累加，且不可修正。

  对lookup的性能影响      低     高，在开始更新之前需要获取所有分片的blocks属性                                        低，分片的blocks属性可以在lookup分片时顺便获取
  -------------------- -------- ------------------------------------------------ --------------------------------------------------------------------------------------------------------------------------

Note:
以上三种方案的blocks属性均使用异步更新的方式，即写请求先返回上层，再更新blocks属性。这个同样是出于不能对性能造成较大影响考虑的。

方案一准确性低，方案二对lookup性能影响很大，因此综合考虑，选择方案三。

### 分片目录存放位置

- 方案一

所有文件的分片均存放在/.shard目录下，/.shard目录下不再分级，该方案是开源代码所使用的。

- 方案二

  如文件路径为：/dir1/file1，则file1的分片将存放在/dir1/.shard/\<gfid\>/\<group\>目录下。

  gfid：首分片的gfid

  group：分片的分组号，从0开始。某个文件的所有分片按组进行存放，每组最多存放1024个分片

- 方案三

  文件的所有分片存放路径为：/.shard/\<xx\>/\<yy\>/\<gfid\>/\<group\>/

  xx：代表gfid的第1/2位

  yy：代表gfid的第3/4位

  gfid：首分片的gfid

  group：分片的分组号，从0开始。某个文件的所有分片按组进行存放，每组最多存放1024个分片

  以下是各方案的对比：

### 全局分片xlator位置

io-retry对主要对读写IO提供重试机制。shard的写IO可能会触发分片创建，io-retry不对create请求重试，因此：io-retry放在shard上层。

io-split用于对大于128K的IO进行切分，如果io-split放在shard上层，对于那些非128K对齐，大小比128K大的IO，可能在io-split和shard层都需要切分。因此：io-split放在shard下层。

### 分片组织形式

引入全局分片后，上层应用所看到的一个文件，在shard下层的xlator看来会变成多个文件（即分片）。这些xlator并不感知这些文件之间的关系，这是由shard管理的。

![图 4‑14 分片组织形式](media/image18.png){width="5.965972222222222in"
height="4.370138888888889in"}

以文件/images/cluster/vm2.vm/vm-disk-1.qcow2为例，
vm-disk-1.qcow2这个文件本身就是首分片。同一个文件的所有分片会被统一存放，存放路径为：

 /.vs/shard/\<xx\>/\<yy\>/\<gfid\>/\<group\>/\<gfid\>.\<index\>.shard

- xx：首分片gfid的第1/2位

- yy：首分片gfid的第3/4位

- gfid：首分片gfid

- group：分片的分组号，从0开始。某个文件的所有分片按组进行存放，每组最多存放1024个分片，某个分片所属的分组号为：
  index % 1024

- index：该分片的分片索引，取值从1开始

/.vs/shard目录及目录下的文件对上层不可见。

### itable

为了保持逻辑简单，shard不维护独立的itable，分片的inode存放在公共的itable中。但由于分片数量较多，需要评估单个客户端最大需要支持的分片数量，并对现有itable相关资源进行调整，以及给出整个系统在极端情况下的资源消耗情况。

考虑第一种情况（单数据盘分片数量达到峰值）：

3主机2副本，每台主机30个数据盘，每个数据盘1万个分片，即shard层需要管理30
\* 3 / 2 = 45万个分片，平均到3个主机，每个主机需要处理15万个分片。

第二种情况（集群分片数量达到峰值）：

数据盘256个，每台主机最多30个数据盘，那么大约有9台主机。整个卷最大支持100万个分片，每个客户端大概需要支持：100万
/ 9 ≈ 12万个分片。

因此，定义每个主机最大支持20万个分片，itable相关内存池资源消耗如下：

  -------------- ----------------------- -------- ------------------------
                 单个内存消耗（字节）    数量     总消耗

  inode_t        252(以2.7为例)          200K     49M

  dentry_t       84(以2.7为例)           200K     16M

  fd_t           220(以2.7为例)          200K     43M

  inode哈希桶    16                      64K      1M

  name哈希桶     16                      14057    220K

  总计                                            109M
  -------------- ----------------------- -------- ------------------------

ctx内存消耗估算：

分片下层大概9个xlator，每个inode ctx和fd ctx假设为1KB，总的内存消耗：

2KB \* 9 \* 200K = 5600M

#### 关键算法描述

全局分片文件大小的计算依赖于扩展属性：trusted.shard.last-index，last-index用于表示某文件最后一个条带组的索引。

![图 4-19 条带宽度\>1](media/image25.png){width="4.957638888888889in"
height="0.90625in"}

上图例子表示的是条带宽度=4，last-index=2的情况，这种情况下的文件大小计算公式为：

文件大小 = 分片大小 \* 条带宽度 \* last-index + last_group_size

last_group_size表示最后一个条带组的大小，这个值的计算步骤如下：

1.  获取最后一个条带组所有分片的大小，记为size\[0\],\...,size\[n\]

2.  计算每个分片所占条带数据块的块数（即分片由多少个128K数据块组成，不满128K的部分按照128K计算），记为cnt\[0\],\...,cnt\[n\]

3.  取出cnt最大且分片索引最大的那个分片相对于当前条带组的索引，记为index（从0开始，最大11）

4.  last_group_size = (cnt\[index\] - 1) \* stripe_size \* stripe_width

5.  last_group_size += (stripe_size \* index) + (size\[index\] %
    stripe_size)

    计算例子：

    ![](media/image26.png){width="3.5618055555555554in"
    height="2.7708333333333335in"}

    图 20 last_group_size计算例子

<!-- -->

1.  每个分片的大小分别为：1G+128K，1G+128K，1G+64K，1G

2.  cnt\[0\] = 8193, cnt\[1\] = 8193, cnt\[2\] = 8193, cnt\[3\] = 8192

3.  index = 2

4.  last_group_size = (8193 - 1) \* 128K \* 4 = 4G

5.  last_group_size += (128K \* 2) + 64K = 4G+320K

由于需要获取最后一个分片或条带组的大小，因此lookup请求会被放大。

### 文件mtime更新

由于文件的属性只从首分片获取，因此当上层业务只写非首分片时，首分片的mtime将得不到更新，最终该文件的mtime会不准确。

为了保证mtime具有一定的精确度，且不产生过多额外的请求，文件最新的mtime缓存在inode_ctx中，并在适当的时机回刷到首分片。回刷时机：

- 定时回刷（时间间隔：1s）

  定时机制采用gluster内部定时器，定时任务执行时判断mtime是否有修改，如果有才发送setattr请求到首分片更新mtime。

- 上层调用flush接口时回刷

### 分片打开、加锁方案

1)  文件打开

考虑到文件最大支持256T，按分片大小16G计算，则会有16384个分片。如果在open文件时把所有分片都打开，然后再返回open请求，则会非常慢。为了保证打开文件的耗时不会因为分片数量增加而增大，分片采用按需open的方式。即：open文件只open首分片，然后open请求返回。后续的IO落在某个分片上，再去open对应的分片。

但是，如果所有分片都是按需open，那么落在这些分片上的第一个IO会非常慢。为了保证主要场景的性能，对于1T以下的文件，打开文件后马上触发所有分片的打开。

2)  排它锁关联处理

两种情况会导致fstat返回的结果不正确：

1.  子卷上线后，读源可能需要切换，但是fstat发生在修复选源之前，因此使用的是旧的读源。如果旧读源是本地副本，那么fstat发送到本地副本会返回成功。

2.  首分片排它锁已失效，但是首分片并没有发生指控（没有写操作），即使触发了修复，也未必能正确修复排它锁的licensed_mark

    为了确保fstat结果的正确性，修改如下：

- fstat接口发送到所有副本，所有副本返回成功时，才返回上层成功；否则触发一次修复，并且本次fstat请求返回失败。

- 修复选源。当文件无指控时，需要选择较多数的licensed_mark来修复其他副本。

- 服务端licensed_mark落盘，并且在第一次lookup时从底层带上来并初始化内存里的值。这个修改用于处理部分brick重启导致licensed_mark丢失的问题。一旦丢失，会影响选源流程。如副本1/2指控副本0，三个副本的licensed_mark分别为：\[
  A B B \]，现在副本2重启，licensed_mark为：\[ A B None
  \]，无法选出多数副本。

### 故障注入机制

程序中的某些分支需要构造故障才能进入，某些故障难以把握构造时机，这个会大大提高测试成本。为了方便对异常分支进行测试，提供一种故障注入机制。该机制主要依赖一个故障注入函数，函数原型如下：

  -----------------------------------------------------------------------
  int shard_failure_inject (enum shard_fi_position position, \...);

  -----------------------------------------------------------------------

该函数的position参数表示某次故障注入位于代码中的哪个位置，此外，该函数接收可变参数，可根据这些参数来决定某个position是否注入故障。在代码中那些难以进入的异常分支之前，调用该故障注入函数，如果函数返回0，不做任何处理；如果函数返回1，进入故障注入分支，该分支改变程序的正常走向，是程序进入异常分支。

为了可以快速修改故障注入策略，此函数最终会调用外部脚本/sf/vs/bin/vst_shard_inject.py，根据此脚本的返回值来决定是否注入故障。

## 删除文件

### 静态结构

删除文件需要处理以下情况：

- 文件删除时间为1ms，不因分片个数的增大而增大

- 文件由多个分片组成，删除文件需要删除多个分片，如何处理部分分片删除失败的情况

为此，将分片的删除处理划分为3个模块，关系如下：

![图
6-2分片删除操作模块关系](media/image51.png){width="4.574305555555555in"
height="1.273611111111111in"}

  ------------------ -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  模块               说明

  文件删除接口       删除接口只处理首分片，其余分片通过分片回收模块进行删除。

  分片回收模块       通过协程启动异步回收任务，完成对某个文件的分片回收。

  垃圾扫描模块       如果分片回收模块在回收过程中发生进程重启，则会产生残留分片。该模块主要处理这种异常场景，通过定时扫描的方式找出需要回收的文件，并启动回收任务。定时时间：默认10min，支持后台可配。
  ------------------ -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

![回收任务流程](media/image54.png){width="4.785416666666666in"

+--------+-------------------------------------------------------------------------------+
| 编号   | 说明                                                                          |
+--------+-------------------------------------------------------------------------------+
| 1      | A锁用于对rename操作和回收任务获取"删除标记文件"的硬链接数进行互斥             |
|        |                                                                               |
|        | 锁的domain为："shard-rename"                                                  |
+--------+-------------------------------------------------------------------------------+
| 2      | B锁用于对多个客户端启动的回收任务进行互斥，确保一个文件只由一个客户端进行回收 |
|        |                                                                               |
|        | 锁的domain为："shard-recycle"                                                 |
+--------+-------------------------------------------------------------------------------+

: 图 6-4回收任务

详细步骤：

1.  对分片目录/.vs/shard/xx/yy/gfid加A锁

2.  获取"删除标记文件"的硬链接数，如果硬连接数\>1，说明该文件还有其他目录项，分片文件不能删除，将"删除标记文件"移除后，解掉A锁，即可返回

3.  如果硬连接数=1，说明此文件可以彻底删除，继续执行第4步

4.  解A锁，加B锁

5.  遍历/.vs/shard/xx/yy/gfid下的所有分片，逐个删除。如果其中一个分片删除失败，则把当前回收任务置为失败

6.  所有分片遍历完成后，如果回收任务仍为成功，则将"删除标记文件"移除

7.  解B锁，本次回收任务结束

- A锁互斥

![unlink与回收任务互斥](media/image55.png){width="4.860416666666667in"
height="2.7118055555555554in"}

在不加A锁的情况下，按照上图的步骤：

1.  应用层发送unlink
    A文件的操作，shard层将其转换为rename操作，A文件rename为/.vs/shard/xx/deleted/gfid（gfid为A文件的gfid）

2.  回收任务获取"删除标记文件"的硬链接数，得到2

3.  应用层发送unlink
    B文件的操作，shard层将其转换为rename操作，成功后文件的硬链接数变为1

4.  回收任务将"删除标记文件"删除，这种情况会导致分片文件残留

height="7.475in"}

### 关键算法描述

通过两阶段来降低删除操作的耗时，同时为了保证不会残留垃圾分片，引入了"删除标记文件"，定时扫描任务最多只需扫描256个目录即可处理完所有需要回收的分片，提高了效率，减少无谓的扫描。

### 处理流程

<figure>
<img src="media/image59.png" style="width:1.26597in;height:5.31944in"
alt="read流程" />
<figcaption><p>图 6-8 shard readv流程</p></figcaption>
</figure>

具体流程：

1.  对原始IO进行切分，得到每个子IO的分片索引，分片内偏移，子IO大小，详细的IO切分逻辑见下面的算法描述部分

2.  获取子IO的fd

3.  下发子IO到下层xlator

4.  判断是否所有子IO已经下发完毕，如果是则进入下一步，否则调到第2步继续处理剩余的子IO

5.  等待所有子IO返回

6.  合并子IO并返回给上层xlator

子IO合并需要处理以下情况：

1.  所有子IO返回成功，则IO返回成功

2.  如果一个子IO失败，那么原始IO返回失败

3.  所有子IO返回成功，但是部分子IO的返回值小于真实下发的子IO大小，这种情况原始IO返回失败

    第2/3种情况使原始IO返回失败是因为io-retry对于返回部分数据的情况一样会重试，而返回失败处理起来比较简单。

### 关键算法描述

算法中用到的两个概念及其计算方法：

条带组大小：条带深度 \* 条带宽度

分片组大小： 分片大小 \* 条带宽度

- 文件偏移到分片索引的转换（offset_to_shard_idx）

  ------------ ----------------------------------------------------------
      输入     offset：文件偏移

      输出     offset所对应的分片索引
  ------------ ----------------------------------------------------------

| [// 此函数同时需要处理旧文件格式和新旧文件格式]{.mark}                                                       |
|                                                                                                              |
| [function offset_to_shard_idx **(**offset**)**]{.mark}                                                       |
|                                                                                                              |
| [//                                                                                                          |
| 条带宽度、条带深度、分片大小、前置分片参数可以从shard_attr_t中获取，下面直接使用文字描述，不引用attr]{.mark} |
|                                                                                                              |
| []{.mark}                                                                                                    |
|                                                                                                              |

|                                                                                                              |
| [ // 条带宽度=1是特殊情况，可能会包含前置分片]{.mark}                                                        |

|                                                                                                              |
| [ end]{.mark}                                                                                                |

|                                                                                                              |

|                                                                                                              |

### 处理流程

<figure>
<img src="media/image63.png" style="width:4.95in;height:8.13889in"
alt="write流程" />
<figcaption><p>图 6-12写请求流程</p></figcaption>
</figure>

具体流程：

1.  对原始IO进行切分，得到每个子IO的分片索引，分片内偏移，子IO大小，详细的IO切分逻辑见下面的算法描述部分

2.  获取子IO的fd

3.  下发子IO到下层xlator

4.  判断是否所有子IO已经下发完毕，如果是则进入下一步，否则调到第2步继续处理剩余的子IO

5.  等待所有子IO返回

6.  合并子IO，并且得出IO合并结果，IO合并需要处理以下情况：

- 所有子IO返回成功，认为原始IO成功

- 如果一个子IO失败，认为原始IO失败

- 所有子IO返回成功，但是部分子IO的返回值小于真实下发的子IO大小，这种情况认为原始IO失败

7.  异步更新blocks，此步骤不关心返回结果

8.  根据IO合并的结果，判断是否继续处理，如果原始IO已认为失败，那么此处返回IO失败

9.  更新文件大小，如果这一步更新失败，那么IO返回失败

### 处理流程

全局分片将扩展属性分为两大类：

- 全局扩展属性：即需要设置到所有分片的扩展属性，目前有分层优先级扩展属性

- 普通扩展属性：只需设置到首分片

  普通扩展属性只设置到首分片，无需特殊处理。

  而对于全局扩展属性，为了保证setxattr请求的耗时不随着分片数量增加而增加，在对首分片设置完成后，该请求就返回。为了确保其他分片的扩展属性与首分片保持一致，两个地方需要做额外的处理：

<!-- -->

- open分片时

  在open分片时，最后会通过fstat接口判断首分片的排它锁是否依然有效，可借助fstat接口将首分片的全局扩展属性获取上来。一旦发现首分片含有全局扩展属性，则将其设置到所打开的分片上。

- 创建新分片时

nfs作为最顶层的xlator，承担了管理itable的职责，而shard使用公共itable来保存分片的inode，因此nfs可以在itable中找到并操作inode。

/.shard目录由shard
xlator维护，因此不允许上层对该目录进行访问，对该目录进行lookup会返回失败。如果应用层发起了对/.shard目录的lookup，shard返回失败，而nfs则会触发一次fresh
lookup，在触发fresh
lookup之前会先把/.shard目录的inode删除。最终导致shard
xlator在解析分片目录或某些分片的inode时，由于/.shard目录的inode被删除而失败。

因此，NFS需要以下修改：

1.  nfs3svc_lookup禁止对/.shard目录进行lookup，一旦检测到，直接返回EPERM错误。

### io-stats

io-stats只是用于统计时延，无关联。

### io-retry

无关联。

### io-split

io-split负责将大IO以128K为单位切分为小IO。它对IO的切分并不影响shard对IO的切分，无关联。

### ssd-cache

shard需要定时调用fsetattr接口，将最新的mtime更新到首分片。读缓存使用mtime来判断缓存数据是否有效，而当前读缓存只实现了setattr接口。

为了防止首分片的读缓存失效，需要为ssd-cache增加fsetattr接口，处理更新文件mtime的情况。

### qemu-lvm

qemu-lvm对fsync接口做了一个特殊处理：如果是BD类型文件，那么fsync请求直接返回，不再发到下层。

在2副本3+主机的场景下，全局分片功能开启，而qemu-lvm
xlator会去掉，这个处理移到shard中。

### afr

1.  shard内部使用fxattrop接口更新某些扩展属性，当前afr的fxattrop接口非事务类型，没有仲裁机制保证，有副本失败时不更新指控，一旦发生修复，可能会导致shard的扩展属性被修错。因此需要将afr_fxattrop/afr_xattrop接口修改为事务类型接口。

2.  fstat判断文件排它锁是否有效需要确保结果准确。目前无法保证这个效果，需要修改为对所有副本发送fstat请求，满足quorum的情况下才认为成功。

3.  无指控情况下的数据修复，需要确保修复选择的owner_mark是正确的。

### 快修

当前快修模块为新建的文件默认生成20K的快修位图和4M的快修log，此大小的快修位图可支持文件大小为512G的文件。而引入全局分片后，底层每个磁盘最大需要支持1万个文件，需要把快修位图和log占用的磁盘空间限制在5G左右。

因此，快修模块做如下修改：

申请位图默认申请128个（加上头部和对齐后的空间，占用4K），快修log默认申请1024个（占用512K）。

### posix

shard需要提供通过分片路径或分片gfid，查找首分片路径的API。该功能需要posix支持，需将posix的update-link-count-parent选项默认打开。

### 底层文件系统xlator

全局分片的部分属性（文件大小，文件blocks属性）存放在扩展属性中，因此调用fstat/stat接口时，需要底层将全局分片的相关扩展属性一并返回。

这是对底层文件系统xlator的一个约束，即对于接口：

int32_t xxx_fstat (call_frame_t \*frame, xlator_t \*this, fd_t \*fd,
dict_t \*xdata)

必须要将xdata中指定的扩展属性获取并返回给上层

## 遗留问题解决

说明在总体设计过程中尚未解决的各个问题的解决方案。

说明在上一个版本未解决的应该在本模块中解决的各个遗留问题的解决方案；

1.  文件无法使用整个卷的空间

    通过在客户端分片，再配合分布框架和分布算法，可以使分片在卷内所有主机上分布，从而使用整个卷的空间。

2.  单个文件只能使用单个SSD的性能

    引入条带化功能后，分布算法会优先将条带组内的分片分布在不同磁盘组上，因此可以使用多块SSD的性能。

# 其他

## 模块**缺陷**列表

1.  文件mtime有1s延迟

2.  在写完非首分片数据之后，进程重启，不能及时更新mtime到首分片

3.  文件的ia_blocks属性不确保准确

4.  某个分片的第一次IO由于需要打开分片，会特别慢

5.  truncate不支持缩小

6.  多客户端，一个客户端追加写，一个客户端读，读客户端返回的stbuf不能反应文件的实时大小

7.  rename操作无法保证原子性，操作失败时会有目的文件被删除，而源文件还没被重命名为目的文件的情况
