# 介绍

## 目的

本文档描述了数据迁移和数据重建的基本原理、工作流程以及详细的实现方法，用于指导后续的编码、测试、维护等工作。需要阅读人员具备GlusterFS相关基础，需要了解VS2.8以及全局分片和新的分布框架，本文档的使用对象包括但不限于VS3.0.0版本相关：编码人员、维护人员、测试人员。

# 概要说明

## 背景描述

aSAN2.x版本迁移/重建的主要问题：

1.  重建需要"热备盘"；

2.  无法利用集群现有剩余空间；

3.  数据拷贝效率低，无法实现多盘并发；

4.  迁移/重建数据量大，时间长，故障时单副本裸奔时间长；

5.  重建过程，业务数据一致性存在较大风险。

    以上问题的出现是因为老版本的基础架构和固定运行图造成的，在vs3.0.0版本中，通过全局分片和全新分布式基础架构提供支持，重新实现按照文件分片的一个副本为粒度的灵活的迁移/重建方式。重建依托afr的修复一致性保证创建中业务数据一致性，迁移是依托业务双写机制保证迁移过程中业务数据的一致性。

### 数据重建原理

aSAN2.x及以前版本中，数据副本故障只能以整个复制组为粒度执行，如果其他复制组上没有多余空间无法创建，此时单副本运行。在vs3.0.0版本全新的分布式基础框架支持下，数据重建以文件的某分片的某一个副本为粒度执行重建，而且可以在感知故障后随时启动重建，并且实现多盘并发重建，降低故障场景单副本裸奔的时间窗，增强产品可靠性，同时依托afr的数据修复的一致性保障重建中数据一致性。

### 数据迁移原理

Vs2.8及以前的版本中，数据迁移以整个复制组为粒度执行迁移，迁移中整个文件的业务都受到影响，而且因为迁移数据量太大造成迁移持续的时间非常长。Vs3.0.0版本中，迁移以文件某分片的某一个副本为粒度，迁移中对业务的影响不再是整个文件，每次迁移的数据量降低，迁移持续时间变短，提升用户体验，增强产品的市场竞争力。

## 方案选型

### 路由切换

新框架下，业务请求的分发不在是以散列计算为依据，而是通过数据路由信息为依据。迁移/重建完成后，业务请求需要按照迁移/重建后的副本分布位置进行分发。因此，迁移/重建完成后需要主动完成路由信息在持久化存储端的更新（路由切换）。实现路由切换的方案目前考虑以下两种：

方案1：直接切换稳态路由到目录空间和数据空间，路由变更过程：

v1\[0,1,2\]\--\>v2\[0,1,3\]。

![](media/image10.png){width="3.9784722222222224in" height="1.6875in"}

图5.路由切换方案1

方案2：先切换中间态路由到目录空间和数据空间，触发重建后再将中间态路由转换成稳态路由，路由变更过程：v1\[0,1,2\]-\>v2\[0,1,(2,3)\]\--\>v3\[0,1,3\]。

![](media/image11.png){width="3.9784722222222224in"
height="3.145138888888889in"}

图6.路由切换方案2

路由切换是迁移/重建的一个事务，但是当前框架并没有基础组件保证多步操作的事务性，能做到达成功能的前提下减少操作步骤，可以减少事务中间失败带来的影响。两种方案对比如下表所示（括号中的数字代表优势权重，1为最低，5为最高）：

方案1：在route层实现路由切换后触发afr的全量修复达成数据副本的重建目的。

### 迁移的实现

方案1：独立客户端进程实现迁移，迁移任务全部在迁移客户端中运行，迁移触发后启动迁移客户端进程，结束后退出。

方案2：迁移用协程实现，迁移协程由vclnt在触发迁移的时候启动，迁移任务结束后协程退出。

图25.数据迁移中业务三阶段处理流程

- **迁移进行中（migrate_in_progress）**

1.  通过获取inode_ctx2判断是否执行过open处理

2.  判断mig_to是否和上次缓存的last_mig_to一致(处理业务进程两次写跨过单个文件多次迁移)

3.  如果不一致表明，迁移目的发生变化，需要先关闭上次的目的fd和锁操作等

4.  一致则判断是否已经执行过in_progress操作，调用target_fn进行处理

5.  未执行过in_progress操作，则对inode所有bind的fd进行查看，如果该fd有在源端打开或加锁，则对目的端进行同样的操作；同时标记该inode已经处理过

6.  更新本次操作的mig_to，调用target_op将请求再次发往目的

- **迁移正常完成（migrate_complete_deal）**

1.  lookup更新业务客户端路由信息(后续操作都发往目的副本)

2.  是否处理过(目的fd已经打开)

3.  处理过则需要查看之前打开的目的端是否和当前目的端一致，不一致则需要重新关闭旧目的，打开新目的端

4.  未open则进行open且关闭源端fd

5.  关闭源端fd，重置inode_ctx2

6.  将请求发往目的端brick

- **迁移异常结束（migrate_failed_deal）**

1.  保存当前路由信息，lookup更新业务客户端路由信息

2.  判断保存的和更新后的路由信息是否一致

3.  一致则说明迁移失败导致mig_to残留，此时只需要返回源端请求返回的结果即可

4.  不一致则说明迁移成功了但是迁移进程崩溃导致mig_to残留，此时内存中路由信息已经更新正确，后续操作都发往目的副本，且本次需要发往目的副本

## 模块关联分析

对老模板/老版本/相关联产品的影响，请做分析。可以和对应的模块责任人架构师做交流

### afr

1.  afr扩展属性修复选源和lookup选源需要保障一致性，否则影响路由信息的一致性。

2.  Afr需要处理路由校验返回的特殊错误码EROUTE，原则是只要一个child返回这个错误码，整个IO应该向route返回EROUTE。

3.  Afr下发changelog是dirty值需要保障每个child使用一个单独的内存域，否则vclnt在迁移同步changelog的时候会因为异步交互出现正常场景下dirty值非0的错误。

4.  Afr处理上线事件触发修复需要加业务锁，保障重建切换路由前的创建bad副本和本次上线修复互斥。

5.  afr对元数据修复时需要过滤掉{mig_to，mig_del}扩展属性，不参与修复

6.  数据重建过程需要和afr元数据修复保持互斥

7.  数据迁移过程需要和afr数据修复保持互斥

8.  Afr下发读请求（包括readv，stat，fstat, getxattr, fgetxattr,
    access）实现双读校验。

### 任务中心

1.  重建源端清理依赖任务中心管理磁盘上下线逻辑

### Vclnt

1.  每次业务通过vclnt需要通过字典携带路由的版本号，在服务端执行路由校验使用。

2.  如果更新路由在afr五步事物中间，则可能下发Inodelk加锁是对迁移源brick，但是下发的inodelk解锁是对迁移目的brick，所以在vclnt_inodelk中保留下发锁的child_no，解锁时下发到对应的client_no。也可以解决迁移前加的afr锁，在迁移后解锁

### route

1.  返回EROUTE后，route需要：重新到目录空间加载路由；按照目录空间的路由版本号修复数据空间路由版本号；按照更新后的路由和版本号重新分发当前业务请求。

2.  route在lookup时需要检查目录空间的路由版本和数据空间的路由版本是否一致，不一致的时候需要用目录空间的版本修复数据空间的版本。

3.  route提供更新路由接口，提供重载路由接口

### Client

网络闪断会导致迁移开始的锁失效，如果闪断后重新open又来一个迁移任务，会导致两个迁移任务同时运行。针对这种场景，在reopen时如果发现是迁移进程打开的fd则不reopen，在client_readv中如果是迁移协程且是匿名fd则返回上层失败，从而迁移进程失败退出

### Locks

修改支持路由更新锁（读写锁，不同主机的读也不需要互斥）

### 底层存储格式

是否支持空洞文件，是否有快速获取空洞信息的接口，没有则字节比对方式

### 分层/写缓存

迁移的写流量不过分层和写缓存，防止真正的热点数据被迁出分层

### Posix-lock层

如果路由切是在5步操作中，可能对目的端执行fxattrop时此时是没有inodelk的，以前逻辑会报错失败，现需要配合修改
